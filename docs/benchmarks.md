# Benchmarks

Time and memory of `einvoice-validate` and of Saxon-HE 12.10 running the same official
stylesheets on the same documents. The tables below are generated by `cargo xtask bench`
(source: `xtask/src/bench.rs`); the raw measurements, every run of every command, are in
[`benchmarks.json`](benchmarks.json).

## What is measured

**The whole job, per rule set.** Every document of the rule set's test corpus (the official
examples and test files, and the mutation cases of the corpus, see
[`corpus/README.md`](../corpus/README.md)) goes through every stylesheet of the rule set. The
corpora of Peppol, Factur-X, XRechnung and the French rules are built locally by their fetch
scripts (their files may not be redistributed); the CEN corpora are in the repository. Each
command is one process for the whole corpus:

- **einvoice-validate**: the release build, `--format json --jobs N`, with the built-in rule set
  (`cen-ubl`, `cen-cii`) or a bundle of the rule set's stylesheets and the files they read. This
  is the tool as it validates: the XML check, then for UBL the UBL 2.1 XML schema, then the
  stylesheets. The XML schema is work Saxon-HE does not do. On a corpus with a document nested
  deeper than the default limit of 256 levels (the CII mutation cases), `--max-depth 1024` is
  given, as in the equivalence tests, so that every document is validated.
- **Same work as Saxon-HE**: `einvoice-validate` with one bundle per stylesheet, without XML
  schema, one process per stylesheet. When a stylesheet stops with a dynamic error on a document
  that has no schema errors, `einvoice-validate` gives no verdict and does not run the
  stylesheets after it; Saxon-HE, run once per stylesheet, runs them all. This variant runs every
  stylesheet on every document, as Saxon-HE does. It is measured only where it differs from the
  first (a UBL rule set, or several stylesheets).
- **Saxon-HE**: `java -cp ... net.sf.saxon.Transform -t -threads:N -xsl:STYLESHEET -s:DIR -o:DIR`,
  with the pinned jars of `scripts/fetch-saxon.sh` and the default settings of the JVM (whose
  heap may grow up to a quarter of the physical memory, which shows in its peak memory). The
  command line runs one stylesheet per JVM, so a rule set of k stylesheets costs k JVM starts,
  stylesheet compilations and JIT warm-ups; the times are the sum over the k runs, the peak
  memory their maximum.
- **Saxon-HE, JVM start excluded** (one thread only): the stylesheet compilation time and the
  execution time of each document as Saxon-HE reports them with `-t`, summed. It leaves out the
  start of the JVM and the loading of Saxon's classes, and the documents on which the
  transformation fails (those have no execution time). On several threads the documents' times
  overlap, so this figure is not given there.

**One document**: a small CEN invoice, a new process each time, as a script or a service that
validates one document per process would run it.

Each command runs once as a warm-up, then the given number of times, the tools taking turns.
Times are the median, with the fastest and slowest run. Each run is measured by a helper process
whose only child is the command: wall time from the spawn to the reaping of the process, CPU time
(user and system, every thread and every waited-for child process) and peak resident set size
from `getrusage(RUSAGE_CHILDREN)`, which is what `wait4` returns for the child. The CPU time of
Saxon-HE includes the JIT compiler and garbage collector threads of the JVM, which run beside the
transformation even on one thread. Documents per second are documents (not transformations)
over the median wall time.

"What each tool reported" checks that both tools did the whole job: the number of
transformations stopped by a dynamic error should agree. Saxon-HE can stop on slightly more
documents when it runs many documents in one JVM, as it learns across documents which variables
to evaluate eagerly (see `xtask/src/oracle.rs`).

The machine is described with the results. A run on a machine busy with other work is slower and
noisier, the JVM more so as it runs its compiler and collector threads beside the
transformation: the load average before and after is recorded for that reason, and the spread
of the runs is given with every time.

## Reproduce

```sh
cargo build --release --locked -p einvoice-cli
scripts/fetch-saxon.sh
scripts/check.sh peppol facturx xrechnung fr-ctc     # the fetched corpora (Java, network the first time)
cargo xtask bench --runs 5 --threads 1,8             # add --write to update this page and benchmarks.json
cargo xtask bench --families cen --runs 3            # some rule sets only: all, cen, cen-ubl, cen-cii, peppol,
                                                     # facturx, xrechnung(-ubl|-cii), fr-ctc(-cii|-ubl|-cdar)
```
