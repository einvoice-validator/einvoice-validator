# Benchmarks

Time and memory of `einvoice-validate` validating as its users run it, and of Saxon-HE 12.10
running the same official stylesheets on the same documents. The tables below are generated by
`cargo xtask bench` (source: `xtask/src/bench.rs`); the raw measurements, every run of every
command, are in [`benchmarks.json`](benchmarks.json).

## What is measured

**The whole job, per rule set, as its users run it.** A job is one rule set as
`einvoice-validate --rules NAME` names it: a built-in one (`cen-ubl`, `cen-cii`) or a fetched one
(Peppol BIS Billing, each profile of Factur-X, XRechnung UBL and CII, each rule set of the French
rules, the e-reporting rules apart, which no corpus covers), on every document of the test corpus
its stylesheets have goldens for: the official examples and test files, and the mutation cases
of the corpus (see [`corpus/README.md`](../corpus/README.md)). The rule sets of the French
package that share a corpus (the CII ones, the UBL ones, the two CDAR ones) are each a job of
their own, on the same documents. The corpora of Peppol, Factur-X, XRechnung and the French
rules are built locally by their fetch scripts (their files may not be redistributed); the CEN
corpora are in the repository. Each command is one process for the whole corpus:

- **einvoice-validate**: the release build, `--rules NAME --format json --jobs N`, the command a
  user runs, with the fetched rule sets read from the cache `target/rules-cache`, where
  `einvoice-validate rules fetch` built them (from the files the fetch scripts downloaded, when
  the cache lacks one), as for its users. It loads and checks the rule set, then for each document:
  the XML check; for XRechnung, the scenario of the KoSIT configuration the document matches (a
  document that matches none, or several, is invalid and nothing else runs on it); the XML schema
  of the rule set (UBL 2.1 for the UBL rule sets, CII D16B for `cen-cii` and XRechnung CII, the
  profile's schema for Factur-X, the package's CII D22B, CDAR D22B or Factur-X schema for the
  French CII, CDAR and Factur-X rule sets); then the stylesheets, with the verdict rules of the
  rule set (which findings are fatal, and for XRechnung the levels of the document's scenario).
  On a corpus with a document nested deeper than the default limit of 256 levels (the CII
  mutation cases), `--max-depth 1024` is given, as in the equivalence tests, so that every
  document is validated.
- **Same work as Saxon-HE**: `einvoice-validate` with one bundle per stylesheet of the rule set,
  without XML schema and without scenarios, one process per stylesheet: every stylesheet on every
  document, the work of the Saxon-HE command below. In the first command, a stylesheet that stops
  with a dynamic error on a document without schema errors ends that document's validation (no
  verdict), and with XRechnung a document runs only the stylesheets of its scenario. It is
  measured where it differs from the first: a rule set with an XML schema, scenarios or several
  stylesheets, which is every rule set measured.
- **Saxon-HE**: `java -cp ... net.sf.saxon.Transform -t -threads:N -xsl:STYLESHEET -s:DIR -o:DIR`,
  with the pinned jars of `scripts/fetch-saxon.sh` and the default settings of the JVM (whose
  heap may grow up to a quarter of the physical memory, which shows in its peak memory), for
  each stylesheet of the rule set: the same files, byte for byte, as the rule set
  `einvoice-validate` loads. The command line runs one stylesheet per JVM, so a rule set of k
  stylesheets costs k JVM starts, stylesheet compilations and JIT warm-ups; the times are the sum
  over the k runs, the peak memory their maximum. This is the stylesheet step of the reference
  validators only: Saxon-HE has no XML Schema validation (the reference validators run another
  validator for that step, such as the XML Schema validator of the Java platform), and the
  command line neither selects scenarios nor reads the reports for a verdict. The XML schema,
  the scenario selection and the verdict are work the first command does and this one does not;
  the second command and this one do the same work.
- **Saxon-HE, JVM start excluded** (one thread only): the stylesheet compilation time and the
  execution time of each document as Saxon-HE reports them with `-t`, summed. It leaves out the
  start of the JVM and the loading of Saxon's classes, and the documents on which the
  transformation fails (those have no execution time). On several threads the documents' times
  overlap, so this figure is not given there.

**One document**: a small CEN invoice, a new process each time, as a script or a service that
validates one document per process would run it.

Each command runs once as a warm-up, then the given number of times, the tools taking turns.
Times are the median, with the fastest and slowest run. Each run is measured by a helper process
whose only child is the command: wall time from the spawn to the reaping of the process, CPU time
(user and system, every thread and every waited-for child process) and peak resident set size
from `getrusage(RUSAGE_CHILDREN)`, which is what `wait4` returns for the child. The CPU time of
Saxon-HE includes the JIT compiler and garbage collector threads of the JVM, which run beside the
transformation even on one thread. Documents per second are documents (not transformations)
over the median wall time.

"What each tool reported" checks that both tools did the whole job. The verdicts of
`einvoice-validate` (valid, invalid, or no verdict when a stylesheet stopped with a dynamic
error) are checked, document by document and on every run, against the reference: the run
fails on any difference. The reference is the acceptance table of the corpus for the fetched
rule sets (`acceptance.tsv`, written by `cargo xtask <family>` from the Saxon-HE goldens and
xmllint: the scenario of each document, what the reference validator makes of the findings of
each stylesheet, and xmllint's verdict on the rule set's XML schema), and the Saxon-HE goldens
for the built-in rule sets. Where the table holds xmllint's verdict on the rule set's schema
(XRechnung, Factur-X, the French CII, CDAR and Factur-X rule sets), the XML schema step of
`einvoice-validate` must agree with it on every document but for the differences listed with
their cause in [`schema-disagreements.tsv`](../crates/einvoice-cli/tests/schema-disagreements.tsv),
each of which must occur; for the UBL 2.1 and CII D16B schemas outside XRechnung the corpus records no schema
verdict, and the tool's own is taken (the schemas are checked against xmllint by the tests of
`einvoice-xsd`). The number of transformations stopped by a dynamic error should agree between
the second command and Saxon-HE. Saxon-HE can stop on slightly more documents when it runs many
documents in one JVM, as it learns across documents which variables to evaluate eagerly (see
`xtask/src/oracle.rs`).

The machine is described with the results. A run on a machine busy with other work is slower and
noisier, the JVM more so as it runs its compiler and collector threads beside the
transformation: the load average before and after is recorded for that reason, and the spread
of the runs is given with every time.

## Reproduce

```sh
cargo build --release --locked -p einvoice-cli
scripts/fetch-saxon.sh
scripts/check.sh peppol facturx xrechnung fr-ctc     # the fetched corpora (Java, network the first time)
cargo xtask bench --runs 5 --threads 1,8             # add --write to update this page and benchmarks.json
cargo xtask bench --families cen --runs 3            # some rule sets only: all, the groups cen, peppol,
                                                     # facturx, xrechnung, fr-ctc, fr-ctc-cii, fr-ctc-ubl,
                                                     # or rule sets by their --rules names
```
