# Test corpus

Documents to validate and the results the reference engine gives for them, one directory per
official rule set. The data in the directory of a vendored rule set is derived from the official
artefacts under `artefacts/` and shares their licence (see the README of each directory); the
directories of the fetched rule sets (Peppol BIS Billing, Factur-X, XRechnung, the French rules)
hold only files of the project, their corpora are built locally (see below). This
README, `SVRL-CANONICAL.md` and the mutation catalogues `mutations.toml` and `mutations-cii.toml` are part of the project
(MIT); the documents the catalogue derives from the official examples share the licence of
those examples.

## Cases

`<rule set>/cases.tsv` lists every case, one per line after a header, tab-separated:

| Column | Content |
|---|---|
| `case` | the case id: `<prefix>/<file>` for a whole document (`examples`, `testfiles`, `snippets`, `national-examples`) or `vefa/<test set directory>/<test set>.<NNN>.xml` |
| `input` | the document, relative to the repository root |
| `kind` | `document` (a whole upstream document), `vefa` (extracted from a VEFA test set) or `xmute` (generated by XML Mutate, XRechnung only) |
| `scope` | VEFA only: the rule ids the test set is about (`<testSet><assert><scope>`) |
| `success` | VEFA only: rule ids that must not fire (`<success>`) |
| `error` | VEFA only: rule ids that must fire with flag `fatal` (`<error>`) |
| `warning` | VEFA only: rule ids that must fire with flag `warning` (`<warning>`) |
| `description` | VEFA only: the test's description, whitespace normalised |

Rule ids are separated by single spaces. Whole documents have only the first three columns. For
an `xmute` case, `scope` is the stylesheet its expectation is about, `error` the rules that must
fail (any flag), `success` those that must not, and `description` the id and description of the
`<?xmute?>` instruction.

### Extraction of VEFA tests

The NNN-th `<test>` (1-based, three digits) of `test/<dir>/<set>.xml` becomes
`vefa/<dir>/<set>.<NNN>.xml`: the XML declaration, then the test's document element copied byte
for byte from the test set. When that element uses namespaces declared by its ancestors in the
test set, those declarations are added to its start tag, so the document has the same
namespaces in scope as in the test set. Each extracted document is parsed back and compared
node by node with the original element. Any structure the extractor does not know (an unknown
VEFA element, a test with no document or two) is an error.

## Mutation cases

`mutations.toml` is a catalogue of edits of a few official documents, each targeting what the
rules check and where engines can diverge: sums and totals off by a cent, rounding of halves,
decimal scale, precision and size, lexical forms of numbers, booleans and dates, VAT categories
and rates, allowances and charges, prices and base quantities, code lists (case, whitespace,
unknown codes), identifiers with check digits (GLN, organisation numbers, IBAN), missing and
repeated elements, credit notes, namespaces and prefixes, comments, CDATA and references in
values, very long values, national rules, and the elements and attributes EN 16931 does not
use. Each `[[mutation]]` has an `id`, a `base` (`invoice`, `credit-note` or `allowances`), a
one-line `reason`, the `edits` and, for the few that apply to one rule set only, `only`. The
edits, their paths and their checks are described in `xtask/src/mutation.rs`; the base
documents of each rule set are named in `xtask/src/ruleset.rs`. `cargo xtask corpus` applies
the catalogue to the bases of each rule set: the result is deterministic, and the documents
keep every byte of their base that an edit does not touch.

`mutations-cii.toml` is the same for the CII syntax, in the same format, applied to the CII rule
set: the same families of edits on five CII examples (bases `invoice`, `single`, `allowances`,
`zero` and `outside`, see the head of the file), plus the charge indicator in every lexical form
(the CII rules cast it to `xs:boolean`), and, for each CII-SR and CII-DT rule of the form
`not(X)`, the element or attribute `X` added where the rule looks for it. Paths in CII edits use
the prefixes `rsm`, `ram`, `udt` and `qdt`.

`<rule set>/mutations.tsv` lists the mutation cases, one per line after a header,
tab-separated: `case` (`mutations/<id>.xml`, also the document's path in the corpus
directory), `input` (relative to the base directory, as in `cases.tsv`), `base` (the id of the
base case) and `reason`. `cases.tsv` lists only the upstream cases.

Saxon-HE stops on some mutation cases with a dynamic error (an amount that is not a decimal, a
field given twice where a rule expects one value). Their golden is then
`<rule set>/golden/<case id>.error.txt`, two lines: `error <code>` and `message <message>`
(whitespace normalised); an engine is expected to stop with the same error code. Saxon-HE runs
the mutation cases on one thread with `-t`, so that each diagnostic follows the document it is
about; besides those errors, the only diagnostic accepted is the warning Saxon-HE prints when a
template pattern raises an error, which XSLT 3.0 treats as a pattern that does not match.

## Goldens

`<rule set>/golden/<case id>.svrl.txt` is the SVRL that Saxon-HE 12.10 produces when it runs
the rule set's compiled XSLT on the case, in the canonical form of `SVRL-CANONICAL.md` (or, for a
mutation case on which Saxon-HE stops, `<case id>.error.txt`, see above). The invocation, with
all cases of `cases.tsv` copied into one input directory:

```sh
java -cp Saxon-HE-12.10.jar:xmlresolver-5.3.3.jar:xmlresolver-5.3.3-data.jar net.sf.saxon.Transform \
    -xsl:<compiled XSLT> -s:<input dir> -o:<output dir> -threads:<n>
```

Saxon's defaults apply otherwise (no whitespace stripping of the source documents), but for the
clock: every run has `-now:2000-01-01T00:00:00Z`, so that a report recording the time of its run
(the SchXslt reports of XRechnung) is the same on every run. The output does not depend on the
number of threads. A run that prints anything is treated as a failure. The mutation cases (and
the XML Mutate cases, on which Saxon-HE may stop too) are copied into another directory and run
with `-t` instead of `-threads`.

The reports of a stylesheet compiled with SchXslt (XRechnung) start with an `svrl:metadata`
element, which must record the fixed time: their goldens are in version 2 of the canonical
form, which represents it (`SVRL-CANONICAL.md`, `xtask/src/svrl.rs`).

Saxon-HE keeps, in a compiled stylesheet, what it learns of the variables it evaluates over
every document it transforms with it (its `LearningEvaluator`: a variable it has seen read 20
times is evaluated where it is bound from then on): in a run over many documents, a later one
can stop with a dynamic error raised by a value that nothing reads, where alone it would not.
A golden is what Saxon-HE gives on its document alone: a mutation case (or XML Mutate case) on
which the run of all of them stops is run again alone, and that run decides its golden.

## Cross-checks

### With the VEFA expectations

For each VEFA case, the failed asserts and successful reports of the golden must match the
expectations of the test: every `error` id reported with flag `fatal`, every `warning` id with
flag `warning`, no `success` id reported, and no other id of the `scope` reported. Each
disagreement is listed with its explanation in `<rule set>/vefa-disagreements.tsv`
(`case`, `kind`, `rule`, `saxon`, `explanation`); a test fails when the observed disagreements
differ from that list in either direction.

### With XML Mutate and with accepted documents (fetched rule sets)

For an `xmute` case, every `error` id must be reported by the stylesheet named in `scope`, with
any flag, and no `success` id. Published examples and test-suite instances are documents their
reference pipeline accepts: the stylesheets of the profile each declares (BT-24) must report no
failed assert other than one flagged `warning` or `information`, and no successful report
flagged `fatal` or `error`; for XRechnung, the one scenario of the KoSIT configuration whose
`match` the document satisfies names the stylesheets and overrides the level of some rule ids
(`customLevel`), a finding being an error unless its flag or role is `warning`, `warn`,
`information` or `info`, and a document that matches no scenario, or several, is rejected. The
disagreements are listed with their explanation in `<rule set>/disagreements.tsv`, in the
format of `vefa-disagreements.tsv`.

### The acceptance table (fetched rule sets)

`cargo xtask <family>` also writes `<corpus>/acceptance.tsv` in the cache: for every case
(whole documents, test cases and mutation cases), the KoSIT scenario it matches (`-` for none,
or a rule set without scenarios; `several: A | B` when several do), then for each stylesheet,
in a column named after its golden directory, `reject` when one of its findings rejects the
case as the reference validator reads the report, `accept` when none does, `error` when
Saxon-HE stopped on the case, and last `verdict`, the acceptance of the KoSIT configuration
(`-` for the other rule sets). For the Mustang validator and the French rules, a failed assert
rejects unless flagged `warning` or `information`, a successful report when flagged `fatal` or
`error`. For XRechnung, as the KoSIT validator reads the reports (`default-report.xsl`), a
failed assert or a successful report rejects unless its flag or its role is `warning`, `warn`,
`information` or `info`, the levels of the matching scenario first; `verdict` is `reject` for a
document that matches no scenario or several (the validator's fallback scenario), otherwise
`error`, `reject` or `accept` from the stylesheets of its scenario alone (a document with XML
Schema errors is rejected too, which the table leaves to the tests). The `match` expressions of
the configuration are read in their three forms, `exists(/p:R/p:C[ . = 'X'])` (the string
value), `exists(/p:R[p:A/p:B/text() = 'X'])` (a text node child) and
`exists(/p:R[p:A = 'X'])`, and evaluated with their XPath meaning, on xtask's own parser: any
other form is an error. For XRechnung, it also checks that the `[[scenario]]` tables of the
bundles the fetch script wrote are the scenarios of the configuration for their syntax, each
with its namespaces, its `match` as written, its stylesheets and its levels, and that each
scenario's XML schema is the one the bundle runs (for CII, the configuration's copy of the CII
D16B schema must be, byte for byte, the one `einvoice-xsd` embeds) or names unchecked.
`crates/einvoice-cli/tests/rules_equivalence.rs` requires the verdict of every bundle on every
document to be that table's: invalid with schema errors or when one of its stylesheets rejects
the document; for XRechnung, the scenario of each document is the table's, the stylesheets that
ran are its scenario's, and the status is the table's `verdict`.

## Peppol BIS Billing 3.0.22: built locally, not committed

The Peppol BIS Billing 3.0 repository publishes no licence, so its files, and everything derived
from them (compiled stylesheets, extracted documents, goldens), stay out of the repository:
`corpus/peppol-bis-billing-ubl-3.0.22/` holds only `vefa-disagreements.tsv` and a README. The
corpus is rebuilt from pinned inputs in `target/peppol/` by `scripts/check.sh peppol`, which CI
runs too (`.github/workflows/peppol.yml`):

1. `scripts/fetch-peppol.sh` downloads the GitHub archive of the release tag and checks its
   SHA-256 and the commit it records, then compiles `rules/sch/PEPPOL-EN16931-UBL.sch` and
   `rules/sch/CEN-EN16931-UBL.sch` with the ISO Schematron skeleton as packaged in ph-schematron
   (ph-schematron-maven-plugin 10.3.1, goal `convert`, engine `iso-schematron`, run by
   Apache Maven 3.9.16 with strict checksums and a private local repository). Both results must
   have the SHA-256 pinned in the script.
2. `cargo xtask peppol` extracts the cases as above into
   `target/peppol/peppol-bis-billing-ubl-3.0.22/corpus/`, applies the mutation catalogue to the
   Peppol examples there, runs Saxon-HE with each stylesheet (goldens in `golden-peppol/` and
   `golden-cen/`), and cross-checks the findings of both stylesheets together with the VEFA
   expectations, against the committed `vefa-disagreements.tsv`.
3. The equivalence tests of `crates/einvoice-xslt-exec` (`tests/peppol_equivalence.rs`, and
   `tests/mutation_equivalence.rs` for the mutation cases) run both stylesheets with the engine
   on every case; each canonical SVRL must equal its golden, and where Saxon-HE stopped with a
   dynamic error the engine must stop with the same code. Without the cache they print SKIPPED
   and pass, unless `EINVOICE_PEPPOL_REQUIRED` is set, as `scripts/check.sh peppol` does.

Without Java or network access, `scripts/check.sh peppol` prints SKIPPED, except in CI, where it
fails. Its cases are listed in `peppol-bis-billing-ubl-3.0.22/README.md`.

## Factur-X, XRechnung and the French rules: built locally, not committed

The same way, `scripts/check.sh facturx`, `xrechnung` and `fr-ctc` (CI:
`.github/workflows/rulesets.yml`) run `scripts/fetch-facturx.sh`, `fetch-xrechnung.sh` or
`fetch-fr-ctc.sh` (every input pinned by its SHA-256, downloads cached in `target/downloads/`),
then `cargo xtask facturx`, `xrechnung` or `fr-ctc`, which build each corpus in the cache,
write its Saxon-HE goldens and run the cross-checks above, then run the equivalence test of the
family (`tests/facturx_equivalence.rs`, `tests/xrechnung_equivalence.rs` or
`tests/fr_ctc_equivalence.rs` of `crates/einvoice-xslt-exec`): every stylesheet on every case
and mutation case, its canonical SVRL equal to the golden, or the error code Saxon-HE stopped
with, the engine given the clock of the oracle, the code lists the Factur-X stylesheets read
with `document()` and nothing else, and the maximum depth raised for a case deeper than the
default, which must refuse it. Without the cache these tests print SKIPPED and pass, unless
`EINVOICE_FACTURX_REQUIRED`, `EINVOICE_XRECHNUNG_REQUIRED` or `EINVOICE_FR_CTC_REQUIRED` is set,
as the jobs set them. Why nothing of them is committed, what is fetched from where, and the
cases, are in the README of each directory. The fetch scripts also write rule-set bundles
(`bundle.toml`, format 2, the code lists as resources) for `einvoice-validate --bundle`.

`cargo xtask engine-status <family>` runs `einvoice-validate` (`--cli`, by default
`target/release/einvoice-validate`) on those corpora, one stylesheet at a time, and writes, for
each rule set, which cases give the Saxon-HE result, which differ, which fail, and which
stylesheets the engine refuses to load (`<corpus>/engine-status.txt` in the cache); a case
deeper than the default maximum depth runs with `--max-depth 1024`. It reports; it does not
check.

## Commands

```sh
cargo xtask manifest            # vendored files match artefacts/*/SHA256SUMS
cargo xtask corpus              # cases.tsv, vefa/, LICENSE.txt, mutations.tsv and mutations/ match what extraction and the catalogue produce
scripts/fetch-saxon.sh          # Saxon-HE and the XML Resolver from Maven Central, checksums verified, into target/oracle/saxon/
cargo xtask oracle              # Saxon on every case; the goldens must match (needs Java)
cargo xtask crosscheck          # goldens against the VEFA expectations
scripts/fetch-peppol.sh         # Peppol release and its compiled stylesheets into target/peppol/, checksums verified
cargo xtask peppol              # Peppol corpus, Saxon goldens and cross-check, in target/peppol/ (needs Java)
scripts/check.sh peppol         # the two above, then the Peppol equivalence test
scripts/check.sh facturx        # scripts/fetch-facturx.sh, cargo xtask facturx, the equivalence test (needs Java)
scripts/check.sh xrechnung      # scripts/fetch-xrechnung.sh, cargo xtask xrechnung, the equivalence test (needs Java)
scripts/check.sh fr-ctc         # scripts/fetch-fr-ctc.sh, cargo xtask fr-ctc, the equivalence test (needs Java)
cargo xtask engine-status FAMILY  # the engine on the corpora of a family: what passes, differs, fails
```

`--write` regenerates instead of checking (`manifest`, `corpus`, `oracle`); these four commands
work on the committed corpora. `cargo test` runs the manifest, extraction, mutation and
cross-check checks
without Java, and the equivalence tests of `crates/einvoice-xslt-exec`: `tests/cen_equivalence.rs`
runs the vendored stylesheet on every case and its canonical SVRL must equal the golden;
`tests/peppol_equivalence.rs` does the same on the Peppol corpus when it has been built;
`tests/mutation_equivalence.rs` does it on the mutation cases of both, where a golden may also
be a dynamic error, whose code the engine must raise (its message may be worded differently).
`tests/cii_equivalence.rs` does both on the CII corpus; the tests of `einvoice-validator`
(`tests/cii_corpus.rs`) and `einvoice-cli` (`tests/cii.rs`) check the built-in rule set
`cen-cii` and the detection of the syntax on it.
